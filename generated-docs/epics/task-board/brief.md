# Epic: Task board, task detail, and settings

Inherits roles, auth, data source, compliance, and styling from project.md.

**Depends on:** the sign-in epic (this board lives inside the signed-in surface; a signed-in team member is a precondition for every workflow below).

---

## Goal

A signed-in team member sees tasks grouped across To do / In progress / Done, filters by assignee, creates / edits / moves / deletes a task, and sets their own display name.

---

## Data Model

Scoped to this epic (mock-only — no backend; see project.md §Data Source).

**Task**

| Field | Type | Notes |
|---|---|---|
| `id` | string | Generated by the mock data layer on create |
| `title` | string | Free text |
| `assignee` | reference | Points at an Assignee/User; see BR2 and Notes & Caveats (source of the assignee set is unspecified in the design) |
| `status` | enum | `To do` \| `In progress` \| `Done` |
| `dueDate` | date | Displayed in ISO format (e.g. `2026-05-01`) — see Notes & Caveats |

**Assignee / User** (the current signed-in user, and the pool of assignable people)

| Field | Type | Notes |
|---|---|---|
| `displayName` | string | Editable on Settings |
| `initials` | derived | Rendered on Board cards; derivation rule not specified by the design — see Notes & Caveats |

Both entities are inferred from the digest's Data Shapes section (no schema file shipped with the design).

---

## Functional Requirements

- **R1:** Board screen (landing) shows three columns — To do / In progress / Done — each holding task cards. A card shows the task title and the assignee's initials. A primary "New task" button sits top-right. An "All assignees" filter dropdown top-left filters cards by assignee. Empty-column copy reads "Nothing here yet". The Done column header is `--color-done` (`#16a34a`); the active column header uses primary blue (`#2563eb`).
- **R2:** Task detail screen opens when a card is clicked, and views/edits one task. Fields: Title (text), Assignee (dropdown), Status (To do / In progress / Done), Due date (date, displayed ISO, e.g. `2026-05-01`). Buttons: "Save changes" (primary) and a "Delete task" text link. Moving a task between columns is done by changing Status here (and/or on the board).
- **R3:** Settings screen has heading "Your settings", one field "Your display name" (text), and a "Save" button.
- **R4:** A mock/stand-in task data layer provides CRUD — create, edit, move between statuses, delete. Assignee filtering on the Board reads from this layer. Assignee initials on cards are derived from the assignee's name/display name.

---

## Business Rules

- **BR1:** The Board's assignee filter defaults to "All assignees" (shows every task); selecting a specific assignee shows only that assignee's tasks across all three columns.
- **BR2:** A task card renders the task title and the assignee's initials, derived from the assignee's display name (exact derivation rule — see Notes & Caveats).
- **BR3:** A column with no matching tasks shows "Nothing here yet" instead of cards.
- **BR4:** Changing a task's Status on the Task detail screen moves it to the corresponding Board column; there is no drag-and-drop between columns in this epic.
- **BR5:** "Save changes" persists the edited Title / Assignee / Status / Due date to the mock data layer and returns to the Board.
- **BR6:** "Delete task" removes the task from the mock data layer and returns to the Board.
- **BR7:** "New task" opens the Task detail screen in a create/empty state; saving creates a new task in the mock data layer (default Status: To do, pending confirmation — see Notes & Caveats).
- **BR8:** Settings "Save" persists the display name to the mock data layer for the current user; cards and dropdowns that reference this user's initials/name reflect the update.

---

## Key Workflows

1. **View and filter the board** — user lands on Board, sees tasks grouped into To do / In progress / Done; selects an assignee from the filter to narrow the view to that person's tasks; selects "All assignees" to clear the filter.
2. **Create a task** — user clicks "New task" → Task detail opens in create/empty state → user fills Title / Assignee / Status / Due date → "Save changes" → task appears on the Board in the column matching its Status.
3. **Edit or move a task** — user clicks a card → Task detail opens with that task's values → user edits fields (including Status to move it between columns) → "Save changes" → Board reflects the update.
4. **Delete a task** — user opens a task's detail → "Delete task" → task is removed from the mock data layer and no longer appears on the Board.
5. **Set display name** — user reaches Settings (entry point TBD — see Notes & Caveats) → edits "Your display name" → "Save" → the new name (and derived initials) is reflected wherever this user appears (their own cards/assignee references).

---

## Feature NFRs

- **NFR-1:** Filtering the Board by assignee updates the visible cards without a full page reload (client-side state against the mock data layer).
- **NFR-2:** The mock data layer persists task and display-name state across navigation between Board, Task detail, and Settings within a session, so create/edit/move/delete/rename are consistently reflected everywhere they're referenced.
- **NFR-3:** Column header colours use the design tokens verbatim — Done column header `#16a34a`, active column header / primary actions `#2563eb` — per project.md §Styling & Branding (no ad-hoc hex in components; reference tokens per [styling-centralisation.md](../../../.claude/policies/styling-centralisation.md)).

---

## Out of Scope

- Any real backend or persistence beyond the mock/stand-in data layer (project.md §Data Source: `mock-only`).
- Drag-and-drop of cards between Board columns — moves happen via the Status field on Task detail.
- Multi-user real-time sync (e.g. another team member's edits appearing live).
- Notifications or reminders for due dates.
- Search, sorting, or additional filters beyond "All assignees" / a single assignee.
- Role or permission management — single "Team member" role only (project.md §Roles & Permissions).

## Notes & Caveats

Design choices the digest left open (`generated-docs/design/digest.md` §Uncertainties) — confirm these at PLAN before or during story-writing for this epic:

- **Due-date format:** not specified by the design; defaulting to ISO (`2026-05-01`) per the digest's suggestion. Confirm whether a localized format (e.g. "1 May 2026") is preferred instead.
- **Assignee list source/options:** neither the Board filter nor the Task detail Assignee dropdown enumerates its options in the design. Confirm whether the assignee pool is a fixed seeded list, user-managed, or something else — this affects the mock data layer's shape.
- **Initials derivation:** the design shows initials (e.g. "JD") but doesn't specify the rule. Defaulting to first-letter-of-first-name + first-letter-of-last-name; confirm.
- **Reaching Settings:** no navigation control to Settings appears in the design (Board and Task detail are the only screens with visible navigation). This epic needs to add a nav control (e.g. a header link or avatar menu) not present in the source design — flag this as an addition beyond the digest, not a translation of it.
- **Delete confirmation:** the design doesn't say whether deleting a task requires a confirmation step. Defaulting to no confirmation dialog unless the user requests one; confirm.
- **Validation rules:** no validation or error messages are specified for any field (e.g. is Title required, can Due date be left blank). Confirm expected rules and error copy during story-writing.
- **New task flow:** assumed to open Task detail in a create/empty state (per digest); confirm this is the intended flow rather than, e.g., a separate lightweight "quick add" on the Board itself.

Translate-not-copy — do **NOT** carry these forward from the source design into production (per the digest's "Translate, Don't Copy" section, all directly relevant to this epic's three screens):

- The mockup's placeholder/sample data (a single card titled "Draft launch email" assigned to "JD", and empty Assignee/filter option lists) is illustrative only — build against the real mock data layer, not hardcoded sample content.
- The mockup expresses layout and colour with inline `style` attributes and raw CSS variables — rebuild with the project's design tokens (`globals.css`) and composed Shadcn primitives, not by porting the markup.
- The mockup's buttons, the `<a href="#">Delete task</a>` link, the assignee filter, and the card click are inert placeholder handlers — every one of these needs a real handler wired to the mock data layer.
- The three screens live in a single static HTML file (two panels `hidden`) — rebuild as distinct routed surfaces with real navigation between Board, Task detail, and Settings.
